# B2B 售后运营平台设计规格

日期：2026-08-20

## 1. 背景与目标

公司同时存在项目交付和订阅消费两类业务。销售向售后的客户交接已经通过飞书文档完成；客户服务问题目前由人员填写到飞书多维表格；客户消费数据已经具备采集能力，但缺少统一展示和分析平台。

首期系统定位为：保留飞书作为协作与信息入口，建设独立 Web 平台作为售后管理、消费分析和团队效能中枢。

首期解决以下问题：

- 将客户、服务问题、消费和负责人统一关联。
- 展示客户消费趋势、异常变化和风险信号。
- 透明呈现售后人员的工作量、处理效率和服务质量。
- 建立可追踪的服务问题处理过程，降低遗漏和积压风险。
- 为后续飞书 API 同步、客户健康度和智能分析预留边界。

## 2. 范围

### 2.1 首期功能

1. 售后总览
2. 客户中心及客户详情
3. 服务问题中心
4. 消费分析
5. 售后团队效能分析
6. 基础数据、角色权限和系统配置
7. 客户、服务记录的批量导入
8. 对现有消费数据源的只读接入或汇总接入

### 2.2 首期不做

- 微信、钉钉消息自动抓取
- 飞书多维表格实时同步
- AI 自动回复
- 复杂的流失预测模型
- 完整财务或合同审批
- 面向客户的独立服务门户

飞书多维表格同步仅保留适配器接口，待首期平台稳定后实现。

## 3. 用户与权限

### 售后人员

- 查看被授权的客户及消费概况
- 新建、编辑、处理和转交服务问题
- 记录处理过程、解决方案和客户跟进
- 查看个人工作台和个人效能指标

### 售后主管

- 查看团队全部客户、问题和消费数据
- 分配负责人、调整优先级和处理升级问题
- 查看团队效能、积压、超时和客户风险
- 配置问题分类、SLA 和客户标签

### 销售

- 查看本人负责客户的基本资料和售后状态
- 查看客户的服务问题概要
- 不默认查看其他销售负责的客户

### 管理员

- 管理用户、角色、组织和数据权限
- 管理数据源、导入任务和系统字典
- 查看操作日志

权限采用 RBAC，并补充客户负责人和部门范围的数据权限。合同金额、消费金额等字段支持独立授权。

## 4. 信息架构

### 4.1 售后总览

- 客户总数、服务中客户数
- 待处理、处理中、已解决和已超时问题数
- 平均首次响应时间、平均解决时间、解决率和超时率
- 本月消费、环比变化和消费下降客户数
- 高频问题分类、风险客户、团队工作量排行
- 所有指标支持下钻到筛选后的明细页

### 4.2 客户中心

客户列表包含客户名称、等级、行业、售后负责人、服务状态、本月消费、消费环比、未解决问题数、最近联系时间、健康状态和风险标签。

客户详情页包含：

- 概览
- 消费分析
- 服务记录
- 项目与合同摘要
- 联系人和跟进记录
- 风险及行动计划

### 4.3 服务问题中心

- 列表、搜索、组合筛选和详情
- 新建、编辑、指派、转交和状态流转
- 处理过程、附件、解决方案和内部备注
- 首次响应、解决时间和 SLA 自动计算
- 历史数据批量导入

首期状态为：待受理、处理中、等待客户、等待内部协作、已解决、已关闭。

### 4.4 消费分析

- 公司层：总消费、趋势、同比和环比
- 客户层：消费排行、增长排行和下降排行
- 单客户层：日、周、月趋势及产品或指标分布
- 规则型异常：消费骤降、连续无消费、接近额度、快速增长、消费下降且问题增加

首期不复制全部消费明细。平台优先读取现有数据源的汇总结果，或通过定时任务将客户、日期、产品维度的汇总写入本系统。

### 4.5 团队效能

- 接收、解决、积压和超时问题数
- 平均首次响应时间和平均解决时间
- 解决率、重开率和客户满意度
- 服务客户数、跟进次数和问题难度分布

效能评价不以处理数量单独排名，页面同时展示效率、质量和工作难度，避免诱导拆分问题或草率关闭。

## 5. 核心数据模型

### 5.1 主要实体

- `users`：用户
- `roles`、`permissions`：角色与权限
- `customers`：企业客户
- `customer_contacts`：客户联系人
- `customer_assignments`：销售、售后负责人及协作关系
- `projects`：交付项目
- `contracts`：合同摘要和服务周期
- `service_issues`：服务问题
- `issue_activities`：状态变化、回复、转交和内部备注
- `issue_attachments`：附件元数据
- `follow_ups`：客户跟进
- `consumption_daily`：按客户、日期和产品维度的消费汇总
- `risk_events`：规则产生或人工登记的风险事件
- `import_jobs`、`import_errors`：批量导入任务及错误明细
- `audit_logs`：关键操作审计日志

### 5.2 服务问题关键字段

- 服务编号、客户、来源渠道
- 问题分类、产品模块、问题描述
- 优先级、影响程度、负责人、协作人
- 状态、创建时间、首次响应时间、解决时间、关闭时间
- SLA 截止时间、等待状态累计时长、是否超时
- 解决方案、根因分类、满意度
- 飞书记录 ID 等外部来源标识

外部来源标识设置唯一约束，保证未来重复同步时能够幂等更新。

## 6. 技术架构与部署

### 6.1 技术选型

- 前端：Vue 3、Vite、TypeScript
- 服务端：NestJS、TypeScript、REST API
- 数据库：复用服务器现有 MySQL
- ORM：Prisma
- 部署：Docker Compose
- 入口：Nginx
- 缓存与队列：首期不强制引入 Redis，需要异步任务时再增加

### 6.2 部署方式

- 前端在本地开发，通过 Vite 代理请求远程 API。
- NestJS、MySQL 和 Nginx 运行在 `121.196.154.93`。
- MySQL 不向公网开放，仅允许服务器本机或 Docker 内部网络访问。
- 后端仅监听服务器内部地址，由 Nginx 暴露 `/api`。
- 开发阶段可使用 IP；正式环境使用域名和 HTTPS。
- 密码、JWT 密钥和数据源凭据只存放在服务器环境变量，不进入 Git。

### 6.3 模块边界

- `auth`：身份认证和会话
- `users`：用户、角色和组织
- `customers`：客户、联系人和负责人关系
- `issues`：服务问题、活动记录和 SLA
- `consumption`：消费汇总查询和异常规则
- `analytics`：总览及团队效能聚合
- `imports`：文件校验、预览、导入和错误报告
- `integrations`：现有消费数据源及未来飞书适配器
- `audit`：关键操作日志

各模块通过服务接口交互，控制器不直接跨模块访问数据库。

## 7. 数据流

### 7.1 服务问题

用户在系统内录入或批量导入记录。服务端校验客户、负责人、状态和时间字段后写入服务问题，并记录活动日志。状态或负责人变化时重新计算 SLA 和效能指标。

后续飞书适配器通过外部记录 ID 拉取增量数据：不存在则创建，存在则按更新时间更新；无法匹配客户或人员的记录进入导入错误队列，不静默丢弃。

### 7.2 消费数据

消费模块通过只读凭据连接现有数据源，或接收现有系统提供的 API。定时任务按客户、日期和产品维度计算汇总，并写入 `consumption_daily`。页面只查询本系统汇总表，避免分析请求影响现有生产数据源。

### 7.3 分析指标

总览和效能指标由服务问题、活动记录、消费汇总和客户负责人关系计算。低数据量时实时聚合；数据增长后再加入定时快照或缓存，不在首期提前复杂化。

## 8. 异常与安全处理

- 导入前提供字段映射和数据预览，整批校验后再提交。
- 无法匹配的客户、人员或非法状态生成可下载错误报告。
- 外部数据同步保存游标、执行结果和失败原因，支持安全重试。
- 所有创建、指派、状态变化、导入和配置修改写入审计日志。
- 删除客户和服务问题采用软删除，避免历史统计丢失。
- API 统一返回错误码和可读错误信息，不向前端泄露堆栈或数据库信息。
- 登录接口限流；密码使用强哈希；接口校验身份、角色和数据范围。
- 数据库每日备份，并定期验证恢复流程。

## 9. 测试与验收

### 9.1 自动化测试

- 单元测试：SLA、消费环比、异常规则、权限判断和导入字段转换
- API 集成测试：客户、服务问题、状态流转、消费查询和效能统计
- 数据库测试：唯一约束、事务回滚、软删除和幂等导入
- 前端组件测试：筛选、表格、表单校验和指标下钻
- 端到端测试：登录、创建客户、创建问题、转交、解决、查看统计

### 9.2 首期验收标准

- 每个客户能够关联明确的销售和售后负责人。
- 服务问题能够完整记录、指派、流转、解决和追溯。
- 历史服务记录能够批量导入，并生成明确错误报告。
- 能查看公司、客户和日期维度的消费趋势及异常客户。
- 能查看每位售后人员的工作量、响应效率、解决效率和积压情况。
- 总览指标可以下钻至对应明细，且统计口径一致。
- 普通售后无法访问未授权客户，敏感金额字段受权限控制。
- 关键业务流程具备自动化测试，部署后能够完成健康检查。

## 10. 实施顺序

1. 建立前后端工程、数据库迁移、身份认证和权限骨架。
2. 完成客户中心和负责人关系。
3. 完成服务问题、活动记录、状态流转和 SLA。
4. 完成历史服务记录导入。
5. 接入消费汇总并完成消费分析页面。
6. 完成售后总览和团队效能分析。
7. 完成审计、安全加固、自动化测试和服务器部署。
8. 平台稳定后实现飞书多维表格增量同步。

## 11. 已确认决策

- 客户类型为 B2B 企业客户。
- 业务同时包含项目交付和订阅消费。
- 采用“保留飞书入口，新 Web 平台统一管理和分析”的建设方式。
- 飞书 API 同步不是首期重点。
- 前端本地开发，服务端和数据库部署到用户服务器。
- 数据库复用服务器现有 MySQL，不新建 PostgreSQL 技术栈。
